How to Access Your Home PC from Anywhere with SSH

Tutorial by @null_djc

If you have ever wanted to get into your home PC from work or from a coffee shop, you probably hit the same wall we did: your home has no fixed public IP and the router lets nobody in. The way out is to use a server that does live on the internet as a jump host (also called a bastion) and have your home be the one that connects to it.

It takes two commands: at home, ssh -R to open a tunnel to the jump host, and away from home, ssh -J to come in through that tunnel. Below we look at why it works, how to keep it running on its own and where we got it wrong at first.

The idea in an example

We have three machines:

  • The home PC, which is the destination. It sits behind the router with no public IP, and its user is ana.
  • The jump host, jump.example.com: a server on the internet (any VPS) with a public IP and SSH.
  • The work PC, or your laptop on the go: where you want to connect from.

What we want is to type ssh home at work and land inside the home PC, as if it were right next to us.

The trap

The first thing we thought of was the obvious one: open port 22 on the router (port forwarding) and connect straight to the home IP. It has three problems:

  1. Often it is not possible. Many internet providers share one public IP among many customers (CGNAT). Your router has no IP of its own to open.
  2. The IP changes. Even with a public IP, it is rarely fixed: one today, another tomorrow, and you need dynamic DNS to keep up with it.
  3. You expose your home to the whole internet. An open port 22 gets login attempts from bots around the clock.

The idea

The router does not let anything in, but it does let things out. So we turn it around: the home PC connects to the jump host and tells it "open your port 2222 and send me whatever arrives there". That is a reverse tunnel (-R).

From work you connect to the jump host and ask it to take you to its port 2222. Your home is on the other side. Along that path travels an SSH connection encrypted end to end between work and your home: the jump host only passes along bytes it cannot read.

There are two connections, and in each one the key is split the same way: the private key stays on the machine that starts the connection and the public key goes in the ~/.ssh/authorized_keys of the machine it connects to.

ConnectionWho starts it (private key)Where it connects (public key)
The tunnelHome PCJump host
The jumpWork PCJump host
Getting into homeWork PCHome PC

No private key ever goes through the jump host.

The solution

1. Prepare the home PC

The home PC needs an SSH server so others can connect to it, and a key to connect to the jump host. On Ubuntu or Debian:

sudo apt install openssh-server
ssh-keygen -t ed25519

The public key ends up in ~/.ssh/id_ed25519.pub. On the work PC you do the same with ssh-keygen, and its public key goes in the ~/.ssh/authorized_keys of the home PC. Do that step while you are at home.

2. A user just for the tunnel on the jump host

On the jump host we create a separate user, tunnel, so it does not get mixed up with the user you manage the server with:

sudo adduser --disabled-password tunnel

Its /home/tunnel/.ssh/authorized_keys holds both public keys, each one with the only thing it is allowed to do:

restrict,port-forwarding,command="/bin/false",permitlisten="localhost:2222" ssh-ed25519 AAAA... ana@home
restrict,port-forwarding,command="/bin/false",permitopen="localhost:2222" ssh-ed25519 AAAA... ana@work
  • restrict removes everything (terminal, forwarding, agent) and port-forwarding allows only tunnels again.
  • command="/bin/false" makes any command end right away: with these keys the jump host cannot be used for anything else.
  • permitlisten="localhost:2222": home can only open port 2222.
  • permitopen="localhost:2222": work can only go to port 2222.

If someone steals one of those keys, on the jump host they cannot open a terminal, look at files or jump anywhere else.

3. Open the tunnel from home

On the home PC:

ssh -N -R 2222:localhost:22 tunnel@jump.example.com
  • -R 2222:localhost:22: port 2222 on the jump host leads to the SSH (port 22) of your home.
  • -N: no terminal, it just keeps the tunnel open.

That 2222 only listens inside the jump host (localhost). It cannot be seen from the internet, which is exactly what we want.

4. Connect from work

With the tunnel open, from the work PC:

ssh -J tunnel@jump.example.com -p 2222 ana@localhost

-J means "jump through here". That localhost is the jump host's, which is the door to your home, and ana is your user on the home PC.

Typing that every time gets old. In the ~/.ssh/config of the work PC you give each machine a name:

Host jump
    HostName jump.example.com
    User tunnel

Host home
    HostName localhost
    Port 2222
    User ana
    ProxyJump jump

And to get in all you need is:

ssh home

5. Keep the tunnel from dying

If the home internet drops or the PC restarts, the tunnel dies. We set it up as a systemd service on the home PC, in /etc/systemd/system/jump-tunnel.service:

[Unit]
Description=Reverse tunnel to the jump host
After=network-online.target
Wants=network-online.target

[Service]
User=ana
ExecStart=/usr/bin/ssh \
    -N \
    -R 2222:localhost:22 \
    -o ServerAliveInterval=30 \
    -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes \
    -o BatchMode=yes \
    tunnel@jump.example.com
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
  • ServerAliveInterval=30 and ServerAliveCountMax=3: every 30 seconds it checks that the jump host answers. If it fails three times, it disconnects and systemd opens it again.
  • ExitOnForwardFailure=yes: if it could not open port 2222, it exits instead of staying connected with no tunnel.
  • BatchMode=yes: if something asks for a password or to confirm a fingerprint, it fails instead of waiting for an answer that never comes.

BatchMode only applies to the tunnel, which is the connection this service makes. When you connect with ssh home, SSH asks for your password or your key's passphrase as usual. What the tunnel does need is a key without a passphrase, because when it starts on its own there is nobody to type it. That is why that key is limited on the jump host to opening port 2222.

So before enabling it, connect once by hand as ana to accept the jump host's fingerprint. Then:

sudo systemctl daemon-reload
sudo systemctl enable --now jump-tunnel

One detail is left on the jump host. When the home internet drops, the jump host takes a while to notice and keeps port 2222 reserved for the dead connection. Meanwhile, the new tunnel fails again and again. To make it let go quickly, in the jump host's /etc/ssh/sshd_config:

ClientAliveInterval 30
ClientAliveCountMax 3

And restart its SSH with sudo systemctl restart ssh. That way the jump host closes the dead connection within a minute and a half.

Copy files

With the config above, scp and rsync use the name home and go through the jump host on their own:

# a file from work to home
scp report.pdf home:/home/ana/

# a whole folder (only copies what changed)
rsync -av project/ home:/home/ana/project/

Open a home service at work

If a website runs at home on port 8080 (or a database on 5432), you can bring it to the work PC with a tunnel:

ssh -N -L 8080:localhost:8080 home

While that command is open, you go to http://localhost:8080 in your browser and reach the service at your home.

Check it

Before trusting something, we like to see that it really goes where we think. On the home PC, check that the tunnel is alive:

systemctl status jump-tunnel

It should say active (running). From work, with -v, SSH tells you what it is doing:

ssh -v home

Among everything it prints, look for these lines:

debug1: Setting implicit ProxyCommand from ProxyJump: ssh -v -W '[%h]:%p' jump
Authenticated to jump.example.com ([203.0.113.10]:22) using "publickey".
Authenticated to localhost (via proxy) using "publickey".

The first says it will use the jump host, the second that it got into the jump host and the third that it got into your home through the jump host (via proxy).

Is your connection post-quantum?

Someone could record your encrypted connection today and keep it until there is a quantum computer able to decrypt it. Against that, SSH agrees on each session's key with a method that resists those computers. To see which one it used:

ssh -v home exit 2>&1 | grep 'kex: algorithm'

-v writes its messages as errors; the 2>&1 is so that grep reads them too. You get two lines, one per leg: the second is the one for your home, which is the one that carries your data.

debug1: kex: algorithm: sntrup761x25519-sha512@openssh.com
debug1: kex: algorithm: mlkem768x25519-sha256
  • mlkem768x25519-sha256 or sntrup761x25519-sha512@openssh.com: post-quantum. You are already protected.
  • curve25519-sha256 or another: safe today, but not against that recording. The work PC or the home PC has an OpenSSH older than 9.0; update it.

Your ed25519 key does not change: this depends on the OpenSSH version, not on the key.

If your SSH is old

-J and ProxyJump exist since OpenSSH 7.3, and permitlisten since 7.8 (you can check with ssh -V). If the SSH at work is older, the home block uses the classic form, which does the same:

Host home
    HostName localhost
    Port 2222
    User ana
    ProxyCommand ssh -W %h:%p jump

Windows 10 and 11 already include the OpenSSH client, and it understands -J. The config file is at C:\Users\your-user\.ssh\config.

What to watch out for

  • Do not copy any private key to the jump host. With -J there is no need: the jump host only sees public keys.
  • Do not open 2222 to the internet. The jump host can publish it with GatewayPorts yes and you would skip the -J, but that is the same as opening your home SSH to the whole world, which is what we wanted to avoid.
  • Careful with -A (agent forwarding). While you are connected, anyone with admin rights on the jump host can use your keys. With -J you do not need it.
  • If you see remote port forwarding failed for listen port 2222, the jump host still holds the port for an old connection. With ClientAliveInterval on the jump host it sorts itself out in a while.
  • The fingerprint is confirmed twice. The first time, SSH asks you to accept the jump host's and then your home's, which shows up as [localhost]:2222. If you answer no, you will see Host key verification failed.
  • The jump host has to allow forwarding. It is allowed by default, but if someone set AllowTcpForwarding no on the jump host, the jump fails with administratively prohibited: open failed.
  • Turn off passwords at home. Once you get in with your key, set PasswordAuthentication no in the home PC's /etc/ssh/sshd_config.

What it taught us

That the obvious path (opening a port on the router) is often not possible and, when it is, leaves your home in plain sight. If you flip it around, home calls the jump host with -R, you come in through that tunnel with -J and the jump host is left as a pipe that cannot read anything. With the systemd service and the limited tunnel user, all that is left is typing ssh home wherever you are. Try it first with ssh -v home and look for that via proxy line: when you see it, you know you are getting in the right way.
