Depth-First Search (DFS)

Tutorial by @null_djc

If you've ever solved a problem with graphs, mazes or maps on a grid, you've probably run into three letters: DFS. It stands for Depth-First Search, and it's one of those tools that shows up everywhere: in interviews, on Codeforces and in half of the problems where you have to "walk through something".

The idea fits in one sentence: you go as far as you can down one path and, when there's nowhere left to go, you step back and try another.

The idea in an example

Think of a maze. You pick a corridor and follow it to the end. If you hit a dead end, you go back to the last fork and try a corridor you haven't walked yet. And so on, until you've seen everything.

To avoid walking in circles, you leave a mark at every spot you pass. With that you already have the whole algorithm:

  1. Mark the current node as visited.
  2. For each neighbor you haven't visited yet, run DFS from that neighbor.
  3. When there are no unvisited neighbors left, go back to the previous node. This is called backtracking.

The graph we'll use

We take an undirected graph with 6 nodes and these edges: 1-2, 1-3, 2-4, 2-5, 3-6 and 5-6. We store it as an adjacency list: for each node, the list of its neighbors.

1: 2, 3
2: 1, 4, 5
3: 1, 6
4: 2
5: 2, 6
6: 3, 5

We start at node 1 and check the neighbors in list order.

The trap

The first thing we thought was: "I start at 1, then visit its neighbors 2 and 3, and then their neighbors". Nope, that's a different algorithm (BFS, breadth-first search). DFS doesn't finish with the neighbors of 1 before moving on: as soon as it finds a new neighbor, it dives in all the way down.

Look at the actual walk:

  1. We visit 1. Its first unvisited neighbor is 2: we dive in.
  2. We visit 2. 1 is already marked, so we go down to 4.
  3. We visit 4. Its only neighbor is 2, already marked: dead end, we go back to 2.
  4. From 2, 5 is left. We visit it.
  5. From 5, 2 is already marked; we move on to 6.
  6. From 6 we reach 3. Its neighbors (1 and 6) are already marked, so we go all the way back to the start.

The order is 1, 2, 4, 5, 6, 3. 3 is a direct neighbor of 1 and still comes last, because we reach it from 6 at the end of the long path. That's the "depth".

The recursive solution

The most natural way to write it is with recursion: the call stack takes care of remembering which node to go back to. All three versions print the same order we got by hand.

C++

#include <iostream>
#include <vector>
using namespace std;

vector<vector<int>> graph;
vector<bool> visited;

void dfs(int node) {
    visited[node] = true;
    cout << node << ' ';
    for (int neighbor : graph[node]) {
        if (!visited[neighbor]) dfs(neighbor);
    }
}

int main() {
    int n = 6;
    graph.assign(n + 1, {});
    visited.assign(n + 1, false);
    int edges[][2] = {{1, 2}, {1, 3}, {2, 4}, {2, 5}, {3, 6}, {5, 6}};
    for (auto& a : edges) {
        graph[a[0]].push_back(a[1]);
        graph[a[1]].push_back(a[0]);
    }
    dfs(1);  // 1 2 4 5 6 3
}

Python

graph = {
    1: [2, 3],
    2: [1, 4, 5],
    3: [1, 6],
    4: [2],
    5: [2, 6],
    6: [3, 5],

visited = set()
order = []

dfs(1)

Rust

fn dfs(node: usize, graph: &Vec<Vec<usize>>, visited: &mut Vec<bool>, order: &mut Vec<usize>) {
    visited[node] = true;
    order.push(node);
    for &neighbor in &graph[node] {
        if !visited[neighbor] {
            dfs(neighbor, graph, visited, order);
        }
    }
}

fn main() {
    let n = 6;
    let edges = [(1, 2), (1, 3), (2, 4), (2, 5), (3, 6), (5, 6)];

    let mut graph = vec![Vec::new(); n + 1];
    for &(a, b) in &edges {
        graph[a].push(b);
        graph[b].push(a);
    }

    let mut visited = vec![false; n + 1];
    let mut order = Vec::new();
    dfs(1, &graph, &mut visited, &mut order);

    println!("{:?}", order); // [1, 2, 4, 5, 6, 3]
}

Without recursion: with a stack

With big graphs, recursion can blow up the call stack. In Python it happens fast, because the default limit is around 1000 nested calls. The way out is to manage the stack ourselves:

def dfs_iterative(start):
    visited = set()
    order = []
    stack = [start]
    while stack:
        node = stack.pop()
        if node in visited:
            continue
        visited.add(node)
        order.append(node)
        for neighbor in reversed(graph[node]):
            if neighbor not in visited:
                stack.append(neighbor)
    return order

print(dfs_iterative(1))  # [1, 2, 4, 5, 6, 3]

Two details that cost us: neighbors are pushed in reverse (reversed) so they come out of the stack in the same order as in the recursive version, and a node is marked when it's popped from the stack, not when it's pushed. A node can enter the stack more than once, but it's only processed the first time.

How fast is it?

Each node is visited only once and each edge is checked once from each end. With V nodes and E edges, the time is O(V + E) and the extra memory is O(V). In other words, linear: with hundreds of thousands of nodes it fits comfortably within any judge's time limit.

What it's for

  • Checking whether two nodes are connected: run DFS from one and see if you reached the other.
  • Counting connected components: go through all the nodes and, every time you find an unmarked one, start a DFS and add one to the counter.
  • Detecting cycles: if during the walk you reach a node that is still "in progress", there's a cycle.
  • Topological sort: ordering tasks that depend on each other, like which courses to take before others.
  • Grids: counting islands in a matrix, filling an area (flood fill) or solving mazes.

What to watch out for

  • Forgetting to mark: with a cycle in the graph, the program never ends.
  • Marking too late in the recursive version: mark the node as soon as you enter dfs, before looking at the neighbors.
  • The stack in Python: with big graphs, use the iterative version or raise the limit with sys.setrecursionlimit.
  • Asking it for the shortest path: DFS finds a path, not necessarily the shortest one. For that, in unweighted graphs, there's BFS.

What it taught us

That DFS is little code and a lot of use: go all the way down, mark what you've already seen and go back when there's no path left. And that the best way to understand it is to do the walk by hand once, like above, before opening the editor. Then write it from memory, first recursive and then with a stack, and look for it in real problems: on Codeforces you can filter by the dfs and similar tag.
